## راه‌اندازی سریع (۵ دقیقه)

پیش‌نیازها: **Node.js نسخه‌ی ۲۰ یا بالاتر** و یک دیتابیس MongoDB (نصب لوکال یا کلاستر رایگان [MongoDB Atlas](https://www.mongodb.com/atlas)).

```bash
# ۱. کلون و نصب وابستگی‌ها
git clone https://github.com/emiroow/magic-portfolio.git
cd magic-portfolio
npm install

# ۲. تنظیم متغیرهای محیطی
cp .env.example .env.local
# مقادیر MONGODB_URI، NEXTAUTH_SECRET، ADMIN_EMAIL و ADMIN_PASSWORD را وارد کنید

# ۳. بارگذاری محتوای نمونه (اختیاری، پیشنهاد می‌شود)
npm run seed                 # شخصیت پیش‌فرض: frontend
npm run seed -- --persona=backend --force   # انتخاب شخصیت دیگر، با بازنشانی دیتابیس

# ۴. اجرای سرور توسعه
npm run dev
```

نشانی [http://localhost:3000](http://localhost:3000) را باز کنید؛ سایت از همان‌جا `/en` و `/fa` را سرو می‌کند.
داشبورد در `/fa/dashboard` در دسترس است و با همان `ADMIN_EMAIL` و `ADMIN_PASSWORD` وارد می‌شوید — اگر این متغیرها تنظیم نشده باشند، ورود کلاً رد می‌شود.

## حمایت و پرداخت‌ها

صفحه‌ی `/{locale}/support` یک صفحه‌ی مستقل است و از دکمه‌ی hero، منوی داک و نقشه‌ی سایت در دسترس است؛ صفحه‌ی اصلی هیچ بخش حمایتی ندارد و فقط همان دکمه در آن می‌ماند. موضوع این بخش خودِ حمایت است، نه خرید کافی؛ کافی فقط یکی از شکل‌های آن است.

صاحب سایت در داشبورد **روش پرداخت** می‌سازد و از هر نوع فقط یک روش وجود دارد، نه سه قیمت برای یک کار. هر روش یک سیاست مبلغ دارد و به **مقصد‌هایی** تقسیم می‌شود که پول واقعاً می‌تواند به آن‌ها برسد؛ انتخاب مقصد داخل همان ویزارد پرداخت انجام می‌شود.

| روش | چه اتفاقی می‌افتد | مقصد‌های آن |
| --- | --- | --- |
| `پلتفرم حمایت` | ارجاع به یک پلتفرم حمایت — Buy Me a Coffee برای خارج و کافی‌بده برای ایران — یا به صفحه‌ی پرداختی که پیش‌تر در درگاه ساخته شده. پرداخت آن‌جا انجام و دریافت می‌شود. | یک پلتفرم و نشانی صفحه‌اش |
| `کارت به کارت` | شماره کارت و/یا شبا با کد QR تولیدشده در سرور، به‌علاوه شناسه‌ی انتقالِ خود حامی. تأیید دستی در داشبورد انجام می‌شود. | هر تعداد کارت یا شبا که صاحب سایت دارد |
| `ارز دیجیتال` | نشانی روی‌زنجیره یا مقصد لایتنینگ با کد QR، و هشدار شبکه پیش از ارسال. نام هر دفترکل به دو خطه‌ی فارسی و لاتین نوشته می‌شود. | یک نشانی برای هر زنجیره (مثلاً USDT روی ترون، ERC-20، تون) |
| `پرداخت درون‌سایتی` | چک‌اوت کامل داخل سایت: خودِ سایت با v4 زرین‌پال، REST آیدی‌پی، Stripe Checkout یا PayPal Orders v2 تماس می‌گیرد، حامی را به صفحه درگاه می‌برد و در بازگشت پرداخت را سرور‌به‌سرور **تأیید** می‌کند. | هر درگاه تنظیم‌شده به‌عنوان یک مقصد |

نکته‌هایی که باید بدانید:

- **چیزی از مرورگر باور نمی‌شود.** ویزارد مبلغ نامزد و کلید مقصد را می‌فرستد؛ سرور دوباره روش را می‌خواند، کلید را از میان مقصد‌های ذخیره‌شده پیدا می‌کند و هر مبلغ بیرون از `minAmount`/`maxAmount` را رد می‌کند. پس درخواستِ دست‌کاری‌شده نه می‌تواند عدد را عوض کند نه نشانی‌ای را نشان دهد که صاحب سایت ذخیره نکرده است.
- **روش، مقصد و مبلغ، یک انتخاب‌اند.** پنل «مبلغ دلخواه شما» هر جا روشی مبلغ دلخواه را بپذیرد نمایش داده می‌شود و همه‌چیز در همان پنجره انتخاب می‌شود: عدد بدون واحد پولِ مقصدی که آن را می‌برد معنا ندارد، و یک مقصد می‌تواند واحد پول (`variant.currency`) یا بازار (`variant.region`) خودش را داشته باشد.
- **پلتفرم جدید یک خط کد است.** یک شناسه به `SUPPORT_PROVIDERS` در `src/constants/global.ts` و برچسبش در هر دو فرهنگ واژه؛ تا پیش از آن `custom` هر نشانی را می‌پذیرد و نامش را از خودِ مقصد می‌گیرد.
- **پرداخت ماهانه پشتیبانی نمی‌شود.** هر چک‌اوت یک بار حمایت است؛ اگر پلتفرمی خودش اشتراک را مدیریت می‌کند، از همان روش `پلتفرم حمایت` به آن ارجاع داده می‌شود.
- **تأیید، نه رسیدن.** ریدایرکت شدن از درگاه چیزی را ثابت نمی‌کند؛ حمایت فقط پس از موفق‌شدن فراخوانی verify/capture «تأییدشده» می‌شود. مسیر بازگشت idempotent است، پس رفرش یا تکرار callback نمی‌تواند یک حمایت را دو بار بشمارد.
- **دیوار حامیان.** هر چک‌اوت نام (یا ناشناس)، پیام و انتخاب حامی برای نمایش را ثبت می‌کند، به‌علاوه‌ی روش و مقصدی که پول به آن رسیده است. فقط رکوردهای `completed` با اجازه‌ی نمایش، عمومی می‌شوند و نام حامی ناشناس در همان لایه‌ی داده حذف می‌شود تا هرگز به مرورگر نرسد. حمایت‌های کارت‌به‌کارت و ارز دیجیتال تا وقتی صاحب سایت در داشبورد تأییدشان نکند `pending` می‌مانند؛ در همان‌جا شناسه‌ی انتقال کنار مبلغ نشان داده می‌شود.
- **کد QR در سرور ساخته می‌شود** (`qrcode`، به‌صورت data URL تصویر PNG)، پس هیچ میزبان QR خارجی‌ای صدا زده نمی‌شود و اطلاعات حامی از سایت بیرون نمی‌رود.
- **تنظیم‌نشده، نامرئی است.** مقصدِ درگاهی که کلید ندارد در داشبورد علامت می‌خورد و در چک‌اوت دلیلش را می‌گوید؛ روشی که هیچ مقصد آماده‌ی دریافت ندارد، با اعتبارسنجی پیش از ذخیره شدن رد می‌شود.
- **درِ سوءاستفاده.** اندپوینت‌های عمومی بر اساس IP محدود می‌شوند، فیلد honeypot دارند و طول پیام را محدود می‌کنند؛ مبلغ، واحد پول و مقصد همیشه از رکورد ذخیره‌شده خوانده می‌شود.
- **بازار ایرانی و بین‌المللی کنار هم‌اند.** سایت فارسی اول روش‌های ایرانی و سایت انگلیسی اول روش‌های بین‌المللی را می‌چیند (`REGION_ORDER`)؛ یک روش هم می‌تواند مقصد‌های هر دو بازار داشته باشد و در آن حالت ویزارد کنار هر مقصد بازارش را می‌نویسد.

`npm run seed` برای هر روش یک نمونه می‌سازد، با مقصد‌های کاملاً آشکارا جانشین (`your-name`، شبای تمام‌صفر، `TExampleWalletAddress…`) که پیش از ورود به پروداکشن باید در داشبورد عوض شوند. رکوردهای قدیمی‌ای که مقصد جدا نداشتند، هنگام خوانده‌شدن به یک مقصد تبدیل می‌شوند، پس دیتابیس موجود همچنان قابل پرداخت می‌ماند.

## محتوای نمونه

`npm run seed` سایت را با **یک شخصیت کاری** پر می‌کند: یک فرد داستانی که پروفایل، سوابق، پروژه‌ها، ابزارها، راه‌های ارتباطی و نوشته‌هایش همه یک داستان را روایت می‌کنند. با عوض کردن persona، همه‌ی بخش‌ها یکدست بازنویسی می‌شوند؛ می‌توانید مهندس فرانت‌اند، مهندس بک‌اند، توسعه‌دهنده فول استک یا طراح محصول را انتخاب کنید.

| Persona     | چه کسی                                                            |
| ----------- | ----------------------------------------------------------------- |
| `frontend`  | سارا میرزایی — مهندس فرانت‌اند، سیستم طراحی و کارهای RTL          |
| `backend`   | کیان رحمانی — مهندس بک‌اند، پرداخت و پایپ‌لاین رویداد              |
| `fullstack` | الکس کارتر — توسعه‌دهنده فول استک در تیم‌های محصول کوچک           |
| `designer`  | مینا رحیمی — طراح محصول، رابط، سیستم و موشن                      |

```bash
npm run seed:list                              # چه شخصیت‌هایی موجودند
npm run seed -- --persona=designer --force     # پاک کردن دیتابیس و seed همان شخصیت
SEED_IMAGES=false npm run seed                 # بدون تصویر جانشین؛ فقط مونوگرام‌های خود سایت
```

نکته‌هایی درباره چیزی که نوشته می‌شود:

- **هر دو زبان، یک‌جا.** هر رکورد در انگلیسی و فارسی به‌صورت موازی نوشته شده، از جمله تاریخ‌های جلالی در نسخه‌ی `/fa`.
- **پروژه‌ها case study هستند.** هر پروژه بدنه‌ی بلند Markdown، فلگ `featured` (سه مورد برای هر persona که سطر اول صفحه‌ی اصلی را می‌سازند) و `createdAt` صریح دارد تا ترتیب آرشیو و صفحه‌ی اصلی منطق باشد.
- **یک پیش‌نویس در وبلاگ هست.** برای هر persona یک نوشته منتشرنشده درج می‌شود تا حالت draft داشبورد دیده شود.
- **نوشته‌ی «درباره محتوای نمونه» اول می‌آید.** تازه‌ترین پست، هشداری است که محتوای این سایت ساختگی است تا کسی رقم‌های نمونه را واقعی حساب نکند.
- **همه چیز ساختگی است.** نام شرکت‌ها، نشانی‌ها، عددها و تصویرها placeholder‌اند (شخصیت‌های داستانی روی دامنه‌های `*.example.com` و تصویرها از سرویس نمونه‌ی picsum). از طریق `/dashboard` جایگزینشان کنید؛ هیچ‌کدام نقل‌قول‌پذیر نیستند.
- **شخصیت خودتان را اضافه کنید.** یک ماژول جدید در `src/seed/personas/` بسازید که `Persona` export کند و در `src/seed/personas/index.ts` ثبتش کنید — همه‌ی ماژول‌های seed از همان personaی که resolve شده می‌خوانند.

## تصمیم‌های فنی

- **خواندن در سرور، نوشتن در کلاینت.** صفحه‌ها مستقیم از طریق `src/lib/data.ts` می‌خوانند (بدون self-fetch روی HTTP). API عمومی `/api/{lang}` هم برای سرویس‌های دیگر باز است و داشبورد با `/api/{lang}/admin/*` کار می‌کند.
- **یک کارخانه‌ی CRUD.** `src/lib/crud.ts` همه‌ی اندپوینت‌های مدیریتی را می‌سازد: بررسی نشست، اعتبارسنجی Zod، مدیریت اسلاگ، `revalidatePath` بعد از نوشتن و شکل یکسان خطاها.
- **محتوای محلی‌سازی‌شده، نه ترجمه‌شده.** هر مستند فیلد `lang` دارد؛ بنابراین نسخه‌ی فارسی و انگلیسی رکوردهای مستقل‌اند (متن، تاریخ و پروژه‌های متفاوت).
- **بارگذاری تصویر.** در توسعه داخل `public/{type}/{lang}` ذخیره می‌شود و در پروداکشن روی Vercel Blob؛ برش تصویر پیش از آپلود در مرورگر انجام می‌شود و پارامتر ضدکش فقط برای پیش‌نمایش است و در نشانی ذخیره‌شده نمی‌ماند.
- **جریان ویرایش.** هر بخش داشبورد یک پنل لغزان دارد: با باز شدن، بخش به نمای بالا می‌آید (پنل همیشه بالای فهرست است)، با ذخیره‌ی موفق بسته می‌شود، با `Escape` بسته می‌شود و اگر ذخیره رد شود باز می‌ماند تا چیزی از دست نرود.
- **انتخاب پروژه‌های صفحه‌ی اصلی.** گزینه‌ی `active` پروژه را در سایت منتشر می‌کند و `featured` آن را برای بخش پروژه‌های صفحه‌ی اصلی برمی‌گزیند؛ این بخش سه جای ثابت دارد. پروژه‌های برگزیده در صدر ردیف می‌ایستند و جای خالی با جدیدترین پروژه‌ی منتشرشده پر می‌شود، پس هرگز نیمه‌خالی نمی‌ماند؛ و اگر هیچ پروژه‌ای برگزیده نشده باشد، سه پروژه‌ی منتشرشده‌ی جدیدتر نمایش داده می‌شوند. این انتخاب را می‌توان با دکمه‌ی سنجاق در همان سطر پروژه (که بی‌درنگ ذخیره می‌کند و جای پروژه را نشان می‌دهد: «صفحهٔ اصلی · ۱») یا از پنل ویرایش انجام داد. شمارنده همیشه می‌گوید چند جا باقی مانده و هر کنترلی که کار نکند دلیلش را می‌گوید: پروژه‌ی منتشرنشده باید نخست منتشر شود و تا سه جای صفحه پر شده باشد، انتخاب چهارم ممکن نیست.
- **مدل داده.** `profile`، `work`، `education`، `skill`، `social`، `project`، `product`، `blog`، `donation` و `supporter` در `src/models` و تایپ‌های متناظر در `src/types`. پروژه‌ها اسلاگ، متن کامل Markdown، برچسب فناوری، انتخاب برای صفحه‌ی اصلی و فهرست پیوندهای برچسب‌خورده دارند؛ محصولات قیمت، واحد پول، دسته‌بندی، فهرست ویژگی‌ها و وضعیت موجودی؛ نوشته‌های وبلاگ برچسب، تصویر جلد و وضعیت انتشار؛ هر رکورد `donation` یک روش پرداخت است — سیاست مبلغ به‌همراه فهرست مقصد‌هایی که پول به آن‌ها می‌رسد — و رکورد حامیان مبلغ، روش و مقصد استفاده‌شده، وضعیت و آنچه اجازه‌ی نمایش دارد را نگه می‌دارد.
- **پرداخت سمت سرور می‌ماند.** `src/lib/payments.ts` سازگارهای درگاه (v4 زرین‌پال، REST آیدی‌پی، Stripe Checkout و PayPal Orders v2) را با `fetch` ساده و با timeout پیاده کرده است، و هر مبلغ از خود روشِ ذخیره‌شده محاسبه می‌شود. `src/lib/qr.ts` کد QR را به‌صورت data URL تولید می‌کند و `src/lib/rate-limit.ts` اجازه نمی‌دهد اندپوینت‌های نوشتنی عمومی بمباران شوند.
- **قیمت در هر دو زبان درست خوانده می‌شود.** قیمت به‌صورت یک عدد و یک کد واحد پول ذخیره و با `Intl.NumberFormat` قالب‌بندی می‌شود — اعداد و جداکننده‌های فارسی در `/fa` و لاتین در `/en` — و داخل `<bdi dir="ltr">` رندر می‌شود تا دسته‌بندی رقم‌ها هرگز در متن راست‌به‌چپ وارونه نشود. عدد `۰` به‌شکل «رایگان» نمایش داده می‌شود و مرتب‌سازی قیمت تنها وقتی ارائه می‌شود که همه‌ی محصولات یک مقیاس داشته باشند (یک واحد پول، یا جفت ریال/تومان).

## سامانه‌ی طراحی

- **توکن‌های سیاه‌وسفید.** همه‌ی رنگ‌ها در متغیرهای CSS داخل `src/app/globals.css` هستند؛ تأکید هرگز با رنگ ساخته نمی‌شود، بلکه با ضخامت خط، تفاوت سطح و حالت hover معکوس.
- **یک زبان مشترک برای تیترها.** `SectionHeader` سطر شماره + سربرگ + شمارش آیتم، تیتر، توضیح اختیاری و خط باریکی که در جهت خواندن محو می‌شود را می‌سازد؛ بخش‌های صفحه‌ی اصلی و صفحه‌های مستقل هر دو از همان استفاده می‌کنند.
- **قطعات مشترک فهرست‌ها.** `ListingToolbar` (جستجو + چیپ‌های فیلتر)، `FilterChip`، `EmptyPanel` و `Stack` باعث می‌شوند آرشیو پروژه، فهرست محصولات، وبلاگ و فهرست‌های داشبورد یک شکل باشند.
- **RTL شهروند درجه‌یک است.** از فاصله‌های فیزیکی استفاده نمی‌شود (`ps-*`/`pe-*`، `ms-*`/`me-*`، `text-start` و `start-*`/`end-*`)، فلش‌ها با `rtl:-scale-x-100` آینه می‌شوند، letter-spacing در RTL خنثی می‌شود چون پیوند حروف فارسی را می‌شکند، و تکه‌های لاتین داخل متن فارسی با `<bdi>` بسته می‌شوند تا ترتیب دوجهته درست بماند. دیالوگ‌ها و منوهای بازشو بیرون از پوشش زبان نصب می‌شوند، پس `dir` را از `<html>` می‌گیرند و فقط با ویژگی‌های منطقی آینه می‌شوند — بدون فهرست کلاس‌های جدا برای هر جهت. ویرایشگر Markdown با حالت `direction="rtl"` خود کتابخانه کار می‌کند و فونت لاتینِ آن بازنویسی شده تا سطح تایپ فارسی همان فونت سایت را داشته باشد.
- **بی‌حرکتی هم رعایت می‌شود.** انیمیشن‌های ظاهرشدن با CSS (`reveal` / `reveal-view`) و رندر سمت سرور انجام می‌شوند، پس جاوااسکریپت انیمیشنی به کلاینت نمی‌رود و `prefers-reduced-motion` همه‌چیز را خاموش می‌کند.

## شخصی‌سازی

- **رنگ‌ها** — متغیرهای CSS در `src/app/globals.css` تنها منبع تم سیاه‌وسفیدند.
- **محتوا** — همه‌چیز از MongoDB و از طریق داشبورد مدیریت می‌شود؛ با `npm run seed:force` محتوای نمونه بازنشانی می‌شود، یا با `--persona=<id>` شخصیت دیگری را انتخاب کنید (بخش [محتوای نمونه](#محتوای-نمونه)).
- **ناوبری** — نوار شناور، تولتیپ‌ها و فوتر داشبورد هر سه از `NavbarRoutes` در `src/constants/global.ts` خوانده می‌شوند؛ یک تغییر، هر سه را به‌روز می‌کند.
- **افزودن یک بخش** — مدل و تایپ در `src/models` و `src/types`، اندپوینت با `createAdminCrud` در `src/app/api/[lang]/admin/...`، خواندن داده در `src/lib/data.ts` و کامپوننت بخش در `src/components/sections`.
- **زبان‌ها** — ترجمه‌ها در `messages/en.json` و `messages/fa.json` و زبان‌ها در `src/i18n/routing.ts` تنظیم می‌شوند.

## استقرار روی Vercel

1. مخزن را روی GitHub قرار دهید.
2. در [Vercel](https://vercel.com/new) مخزن را import کنید.
3. متغیرهای محیطی را وارد کنید (جدول بالا)؛ برای دیتابیس از رشته‌ی اتصال **Atlas** استفاده کنید.
4. برای فعال‌بودن بارگذاری تصویر، یک فروشگاه [Vercel Blob](https://vercel.com/docs/storage/vercel-blob) بسازید — `BLOB_READ_WRITE_TOKEN` به‌صورت خودکار تزریق می‌شود.
5. استقرار را بزنید، سپس `NEXT_PUBLIC_SITE_URL` را روی دامنه‌ی نهایی تنظیم و یک بار دیگر deploy کنید تا متادیتا به‌روز شود.

در پروداکشن تصویرها روی Vercel Blob و در توسعه داخل `public/` ذخیره می‌شوند؛ برای کار محلی تنظیم اضافه‌ای لازم نیست.

| `npm run seed` فایل `.env.local` را پیدا نمی‌کند | ابتدا فایل `.env.local` را بسازید؛ اسکریپت seed به آن نیاز دارد   |
| روش «پرداخت درون‌سایتی» در چک‌اوت خطا می‌دهد | کلیدهای آن درگاه در `.env.local` نیست؛ برای هر درگاه تنظیمش را ببینید |
| روشی در سایت نیست | هیچ‌یک از مقصد‌های آن شماره کارت/شبا یا نشانی ندارد (اعتبارسنجی با این حالت ذخیره نمی‌کند)، یا خودِ روش منتشر نشده است |

## مشارکت

بازگزارش مشکل و pull request خوش‌آمد است. پیش از ثبت، `npm run verify` را اجرا کنید — همان دروازه‌ای که CI اجرا می‌کند (لینت + تایپ‌چک + بیلد). زبان بصری پروژه را یکدست نگه دارید: توکن سیاه‌وسفید، تیترهای مشترک و فاصله‌گذاری سازگار با RTL.
